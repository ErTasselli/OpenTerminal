# Credit spreads link their two Legs via a nullable `spread_id` on `transactions`, not a new `strategies` table or heuristic grouping

A credit spread is two Transactions on the same underlying/`option_type`/`expiration` — a short Leg (SELL) and a long Leg (BUY) at different strikes — that today land in `transactions` as two completely independent rows, and resolve to two independent Positions under `GET /api/portfolios/:id/positions` in `server/src/routes/portfolio.ts` (confirmed by the existing test "keeps two OPTION positions with different strikes (same symbol/type/expiration) separate" in `server/src/routes/portfolio.test.ts`). We need a way to say "these two rows are one spread" so a later ticket can fold them into a single Position instead of two. We're linking them with a nullable `spread_id` column added to the existing `transactions` table, shared by both legs, rather than introducing a `strategies`/`spreads` table or inferring the grouping heuristically at read time from matching underlying+expiration+opposite-side rows. A column is a one-line addition to the schema this app already has — `transactions` stays the single source of truth, `server/src/db.ts`'s migration loop (the `OPTION_COLUMNS`/`PENDING_ACTION_COLUMNS` pattern) gets one more column added the same way, and the positions aggregation in `portfolio.ts` gains a grouping key rather than a second table it has to join against. Heuristic grouping was rejected because it's ambiguous the moment a portfolio has more than one spread open on the same underlying and expiration with overlapping strikes, or when one leg of a spread has been partially closed by a later, unlinked Transaction — there's no way to infer at read time which SELL pairs with which BUY, so the grouping has to be recorded at write time, not derived. A `spread_id` is also a flat grouping key rather than a 2-leg-specific schema: it generalizes to N-leg strategies (iron condors, etc.) later by simply allowing more than two Transactions to share one `spread_id`, with no migration, whereas a `strategies` table modeled around exactly two legs (e.g. `short_transaction_id`/`long_transaction_id` columns) would need reshaping to support a third or fourth leg.

Two Transactions sharing a `spread_id` must satisfy these invariants to be a valid credit spread, which later tickets enforcing this column will need to check: opposite sides (one `SELL`, one `BUY`); the same `symbol`, `option_type`, and `expiration`; different `strike` values; and a net credit, meaning the `SELL` leg's `price` exceeds the `BUY` leg's `price`. This ADR scopes the decision to exactly 2-leg credit spreads — it does not design for N-leg strategies now, it only notes that `spread_id` as a flat grouping key leaves that door open without a schema change when that need actually arrives.

**Consequence**: this ADR records the linking decision only — no code changes. The `spread_id` column itself, the validation of the invariants above, the change to positions aggregation in `portfolio.ts` to fold linked Legs into one Position, and any UI for entering or displaying a spread are separate, not-yet-tracked tickets built on this decision. N-leg strategies (iron condors and beyond) remain unsupported until a future ticket chooses to allow more than two Transactions under one `spread_id`. Existing single-leg option Positions are unaffected: a Transaction with a `NULL` `spread_id` aggregates exactly as it does today.
