# Image input in AI Assistant chat adds a vision model for Ollama Cloud, not a second Active Provider

The AI assistant's chat feature is gaining the ability to accept an image with a user's turn — pasted or dropped in, most often a screenshot of a chart, an options chain, or a statement — so the model can ground its answer in what's shown, the way a person pastes a screenshot into a chat for a second opinion. We're scoping this narrowly: it's for grounding one chat answer in one pasted/dropped screenshot, not an OCR pipeline the rest of the app can call into, not image generation, and not full parity across both LLM Providers in this phase — image delivery is wired through end-to-end only for `LLM_PROVIDER=ollama-cloud`, even though `ChatMessage.content`'s move from a plain string to text-or-image parts (in `server/src/llm/types.ts`) is a shape both `anthropic.ts` and `ollama.ts` consume, the same shared-neutral-shape pattern tool-calling already established per ADR-0002. We picked this narrow scope because grounding-from-a-screenshot is the concrete, common case worth shipping now, and because committing to OCR-as-a-service, image generation, or simultaneous multi-provider image support before this simpler version has proven out would be scope creep ahead of need — the same reasoning ADR-0002 used to defer brokerage integration and live web search rather than bundle them in.

Ollama Cloud's regular chat model isn't necessarily vision-capable, so an image-bearing turn can't just ride the same model call a text-only turn uses. Rather than model this as a second Active Provider or a runtime provider switch, we added a single-purpose env var, `OLLAMA_VISION_MODEL`, read only inside the `ollama-cloud` provider's own `chat()` call and only when that turn carries an image; it names a vision-capable model for that one call, leaving `LLM_MODEL` as the model every other turn under `ollama-cloud` still uses. A single Active Provider still holds exactly as CONTEXT.md's glossary defines it: `LLM_PROVIDER` still selects exactly one LLM Provider, with no fallback and no runtime/UI selection. `OLLAMA_VISION_MODEL` doesn't add a second provider or a second selectable backend — it's an internal detail of how the already-active `ollama-cloud` provider picks a model per turn, invisible to the chat route and to every other provider. Anthropic's current models already handle image input within the same model used for text, so this provider-internal fork has no reason to exist there — there's no Anthropic equivalent of `OLLAMA_VISION_MODEL` to add in this phase.

**Consequence**: several adjacent pieces are explicitly deferred — full Anthropic image-input parity (translating `ChatMessage`'s image parts into Claude's own multimodal content blocks, so an image-bearing turn under `LLM_PROVIDER=anthropic` is grounded the same way rather than just accepted without effect), any image retention or cleanup policy (images aren't persisted in this phase — they travel in the request only, are never written to disk, and are never embedded as raw bytes in an Audit Log Entry), and any image analysis beyond what the vision model naturally surfaces in its own answer (no separate OCR step, no structured extraction beyond what the model says in its reply).
